# 0044 — Two synthetic fixture packs, and every test that runs a configuration runs against both

## Status

Accepted, 2026-09-18.

## Context

The suite has run against one synthetic configuration since the project started. It is generated by
`tools/gen-fixtures` into the build tree, it runs in about sixty milliseconds, and it is tidy: its
model files sit beside its config, its output is `result.csv` in `results/`, it has no active
intervention and so exactly one scenario, and it names all three of the data pack's diseases.

Every one of those is a fact about that fixture, and the previous run found out what that costs.

- **`GET /api/runs/{id}` reported `"manifest": null` for every real example.** The manifest is named
  after `output.file_name`, which the *configuration* decides; the name the fixture happens to
  produce was hard-coded in three places in the server. **All forty-five server tests passed**,
  because all forty-five used the fixture. It was found by pointing the server at
  `examples/HLM_France`, by hand, after the tests were green.
- A second, smaller instance in the same run: an end-to-end test of the B-24 compatibility flag
  failed because the fixture's policy ran for two years and the defect needs three. There the test
  was wrong rather than the code, which is the better outcome of the two — but it is the same cause.

The pattern is not "the fixture is unrealistic". It is that **a single fixture makes its own
incidental properties untestable**: nothing distinguishes "the code reads the configuration" from
"the code assumes what this configuration says", because there is nothing to disagree with.

## Decision

**Generate a second configuration over the same data, differing on every axis the code could
plausibly have assumed, and run every test that runs a configuration against both.**

`tools/gen-fixtures` writes `<pack>/model` as before and `<pack>/model-b` as well. Both refer to the
same data store as `../data`, so the second pack costs no extra data generation and about a tenth of
a second a run. The differences are deliberate, and each one names something a program might assume:

| | `model` | `model-b` |
|---|---|---|
| model files | beside the config | under `models/`, named differently |
| tables and dataset | beside the config | under `tables/`, named differently |
| `output.folder` | `results` | `out/nested/deeper/results` |
| `output.file_name` | `result.csv` | `synthland_{TIMESTAMP}_B.csv` |
| scenarios | `Baseline` | `Baseline`, `Intervention` |
| active intervention | none | `food_labelling`, with B-24 reachable |
| diseases | all three, in the pack's order | two, reordered |
| `output.comorbidities` | 2 | 1 |
| seed, horizon, cohort fraction | 123456789, 2010–2014, 0.005 | 987654321, 2011–2016, 0.004 |
| `age_range` | the data's, exactly | five years above the data's |

The `{TIMESTAMP}` token is the sharpest of these: the second pack's output is not called
`result.csv`, and it is **not called the same thing twice**. A test that records a name and compares
it to a later run's fails; a test that asks the run what it wrote passes. That is the distinction
the server defect turned on.

**The mechanism** is `tests/support/fixture_packs.h`: a `FixturePack` (an id and a directory),
`fixture_packs()`, a `FixturePackTest` base class, and `HGPS_TEST_EVERY_FIXTURE_PACK(suite)`. A
suite that runs a configuration becomes `TEST_P` and names the pack; adding a third pack is one
edit.

**`FixturePack` deliberately carries no facts about the pack's contents** — not the horizon, not the
disease set, not the scenario names. A test that needs one asks the loaded configuration or the
finished run. That rule is the point: it is what stops a test asserting a constant that only one
pack satisfies, which is the mistake the second pack exists to catch.

The server's `ServedFixture` lays out **every** pack under one configs root, so `/api/examples`
lists two configurations rather than one, and a parameterised test names the one it is driving.

## What it found immediately

Three things, in the first hour, none of which any of the 741 tests then passing would have found.

1. **An age range narrower than the population data's crashed with `map::at: key not found` and no
   location.** The initial cohort is drawn from the population data, while several per-age tables
   are built over the configured range, so a person the data supplies and the range does not cover
   indexes a table with a key it has not got. The baseline reaches the same situation inside a
   parallel loop. This build now refuses at build time with a located diagnostic naming both ranges;
   narrowing the range to mean "simulate only these ages" would be a modelling change, so it is not
   invented here (`src/engine/build_modules.cpp`).

2. **A cancelled two-scenario run started the intervention anyway and simulated a year of it.** A
   scenario's first simulated year happens before its year loop reaches a cancellation check, so
   cancelling after three years of the baseline produced a result file holding a baseline that
   stopped in one year and an intervention that stopped in another — and `years_completed` was four.
   The comment above that code claimed the opposite ("a cancellation that stopped the baseline short
   stops the intervention at the same year, and the pair stays comparable"). The intervention is now
   started only when the run has not been cancelled (`src/sim/engine.cpp`).

3. **The CLI had no test that ran it.** Everything that ran a configuration did so in process with
   the output folder overridden by the harness, so two things the CLI alone is responsible for were
   untested: honouring a configuration's own `output.folder` relative to the working directory, and
   printing the files it wrote by the names it wrote them under. `tests/app/cli_run_test.cpp` runs
   the built binary in a scratch working directory and checks both, against both packs.

It also removed a class of assertion across the suite. `tests/engine/manifest_test.cpp` named
`result_manifest.json`, `result.csv` and a one-element scenario list; `tests/sim/simulation_test.cpp`
named 2010–2014, fifty ages and three diseases by name; a reproducibility test used 987654321 as
"a different seed", which is the second pack's own seed and would have compared a run against
itself. Each is now derived from the configuration under test.

## Consequences

- **The suite is 845 tests rather than 741** — 184 of them in fourteen `Packs/` suites, which is 92
  distinct tests run twice — and the release preset takes about 35 seconds rather than 23.

- **The cost lands hardest on ThreadSanitizer, and it is the largest single consequence of this
  decision.** Of 2,272 seconds of local TSan test time, **2,219 are the 184 `Packs/` tests**; every
  other test in the suite rounds to zero at CTest's one-second resolution. About half of that is the
  second pack, and the `macos · appleclang · tsan` job went from **48m28s before this run to about
  seventy minutes after it**. That job was already the workflow's long pole and the one whose result
  nobody had seen until the previous run.

  Worth being precise about where it came from: the randomised server stress test added in the same
  run, which had an explicit budget of two minutes, is **53 seconds — 2.3% of TSan's test time**. The
  growth is this ADR's, not that one's.

  The obvious mitigation is `ctest -j` on the sanitizer presets: these tests are almost all
  single-threaded and run serially today. It is not done here because changing how CI runs its tests
  at the end of a run leaves no time to find out what it breaks — [docs/backlog.md](../backlog.md)
  carries it.
- **A test that passes on one pack and not the other is a finding about the code**, not a reason to
  narrow the test. All three above were resolved that way.
- **The second pack is not more realistic than the first.** Both are invented; the pack's own
  `SYNTHETIC.md` says so. What the second one is, is *different* — which is the property that
  matters here and the only one claimed.
- **Two packs is not a proof.** A third would find things the second does not, and the real examples
  find things neither does — the server defect came from `HLM_France`, not from a fixture. What this
  buys is that the cheap, fast, always-run layer can no longer be satisfied by a program that
  assumes one particular configuration.
